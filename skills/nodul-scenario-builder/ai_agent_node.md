### AI Agent node

Use `ai_agent` only when the model must choose and call tools dynamically. For deterministic single-turn LLM work, use a normal LLM action.

#### Live-confirmed parameters

- `model`
- `user_prompt`
- `system_message`
- `session_id`
- `force_think_tool`
- `context_window_length`
- `max_iterations`
- `temperature`
- `max_tokens`
- `structured_output`
- `output_json_schema`
- `quick_preview_schema`
- `tools`

Read the current `params` from `search_node_types` before writing.

#### Connector rule

The Agent card has two different outputs:

- **Bottom connector** — this node is an **Agent Tool**. The model decides whether to call it. `fromAIAgent(...)` is valid only here.
- **Right connector** — this is the **next step after the Agent**. It is not a tool. It runs in sequence. `fromAIAgent(...)` fails here (`fromAIAgent used outside of the tool`).

#### How to save through MCP

Both connectors can be saved through MCP.

| What we do | Result |
|---|---|
| Bottom tools only (`parameters.tools`, no node on the right) | Works |
| Same save: bottom tools **and** a right-side node | Works — tools stay nested; the sequential node has `prevNodes` on the Agent |
| Later separate save: add a right-side node after the tools already exist | Works — `parameters.tools` is kept |

#### MCP representation

A correctly connected tool is returned by `get_scenario` inside `AI Agent.parameters.tools`:

```json
{
  "tools": [
    {
      "id": "generated-tool-id",
      "name": "HTTP Tool",
      "typeAlias": "http_request",
      "parameters": {
        "url": "{{ fromAIAgent(\"url\"; \"The URL to request\") }}",
        "method": "GET"
      }
    }
  ]
}
```

The nested tool `id` is generated by the platform.

#### Required MCP creation sequence

Tools may be nested in the first `create_scenario`, together with a right-side sequential node. A two-step save is still valid:

1. `create_scenario`: trigger + AI Agent. Optional: `parameters.tools` and/or a right-side node (`prevNodes` on the Agent).
2. If tools were added later: `update_scenario` with nested tool objects in `parameters.tools`. Right-side nodes may be in the same payload.
3. `get_scenario`: a real bottom tool stays inside `parameters.tools` (it is not a top-level node with `prevNodes` pointing at the Agent). Sequential nodes **do** have `prevNodes` on the Agent.
4. `run_scenario_once` / `get_execution`: the tool name appears in `executedNodesCount`; each right-side node runs once after the Agent.

Set `force_think_tool` to `false` unless a Think tool is also connected on the bottom as a normal Agent Tool.

Do not claim success unless the tool is still nested **and** a run proves `fromAIAgent` works.

#### `fromAIAgent()` syntax

```text
{{ fromAIAgent("paramName"; "description") }}
```

- Arguments use a semicolon.
- The first argument is the tool argument name.
- The second describes what the model should provide.
- Values supplied to action fields are strings.
- It is valid only in a real bottom-connected Agent Tool.

#### Think and Plan tools

Think and Plan are **ordinary Agent Tools**. Connect them only through the Agent's **bottom** connector, in `parameters.tools`, with the same save rules as HTTP or any other tool. They are not sequential right-side nodes.

Do **not** add them by default. Use them only when the user asks, or when correctness/traceability clearly requires extra reasoning. They cost extra tokens and latency.

- **Think Tool** (`__pd_ai_agent_actions_think`) — the agent writes reasoning between steps. With `force_think_tool: true` it is expected on every step; connect only one Think tool. Best when correctness/traceability matter most.
- **Plan Tool** (`__pd_ai_agent_actions_plan`) — one structured plan up front, then follow it. Cheaper/faster than Think, less consistent. Best for medium-complexity or repetitive flows.

Live `search_node_types` for these two aliases includes a required `__$$internal__tool_description` field and a `fromAIAgent(...)` field (`reasoning_log` / `plan_log`). Copy those defaults unless the user wants different wording. That description key is valid **on Think/Plan node types**; it is not a generic key for HTTP or other tools.

Example nested Think tool (same `parameters.tools` array as any other tool):

```json
{
  "name": "Think Tool",
  "typeAlias": "__pd_ai_agent_actions_think",
  "parameters": {
    "__$$internal__tool_description": "Call this tool whenever you have reasoning, intermediate thoughts, or notes between main tool calls.",
    "reasoning_log": "{{ fromAIAgent(\"reasoning_log\"; \"A detailed explanation of your current reasoning, intermediate conclusions, or memory notes.\") }}"
  }
}
```

#### Tool descriptions

`search_node_types` for a standalone `http_request` has **no** Tool Description field. That field exists only after the node is an **Agent Tool** (nested in `AI Agent.parameters.tools`).

On a nested HTTP tool, write:

```json
"__$$internal__tool_description": "GET a public URL and return status and body for the agent."
```

The field is kept on `create_scenario` (nested with the tool) and on a later `update_scenario` of an already connected tool.

`get_dynamic_node_parameters` for `http_request` does **not** return this key (and may error). Do not wait for that tool. Put `__$$internal__tool_description` on the nested tool's `parameters` yourself.

Standalone `http_request` (not under `parameters.tools`) still rejects this key. A top-level `description` on the tool object is not a substitute.

Think and Plan already list `__$$internal__tool_description` in their `search_node_types` schema. Same key, same meaning.

#### Example

Stage 1:

```json
{
  "name": "AI Agent example",
  "nodes": [
    {
      "name": "Start",
      "typeAlias": "run_once",
      "parameters": {}
    },
    {
      "name": "Research Agent",
      "typeAlias": "ai_agent",
      "parameters": {
        "model": "openai/gpt-4.1",
        "user_prompt": "Call HTTP Tool once.",
        "system_message": "Use the available tool when needed.",
        "context_window_length": 25,
        "max_iterations": 3
      },
      "prevNodes": {
        "Start": {}
      }
    }
  ]
}
```

Stage 2 sends the same two-node graph through `update_scenario`, with:

```json
{
  "model": "openai/gpt-4.1",
  "user_prompt": "Call HTTP Tool exactly once with URL https://example.com.",
  "system_message": "Always call the available tool before answering.",
  "context_window_length": 25,
  "max_iterations": 3,
  "temperature": "0",
  "tools": [
    {
      "name": "HTTP Tool",
      "typeAlias": "http_request",
      "parameters": {
        "url": "{{ fromAIAgent(\"url\"; \"The URL to request\") }}",
        "method": "GET"
      }
    }
  ]
}
```

Expected execution:

- AI Agent: 1 execution
- HTTP Tool: 1 execution
- supplied URL: `https://example.com`
- final response reported HTTP 200 and `Example Domain`

#### Runtime data paths and isolation

- Normal runtime references are only `{{$2.text}}` (node **number**). Never `{{$ai_agent_0.text}}`.
- Tools can read upstream main-graph data and earlier nodes in their own tool chain.
- Different tool chains cannot read each other's outputs.
- A normal node after the Agent cannot directly read internal tool-node outputs; it reads the Agent's result.
- No binary/file objects through the Agent tool loop. Return text instead.

#### Testing

1. Test the action with literal, non-destructive values.
2. Build the real bottom tool using the two-step sequence above.
3. Replace model-supplied values with `fromAIAgent(...)`.
4. Force a tool call with a clear prompt.
5. Verify the nested tool remains in `get_scenario`.
6. Verify its execution in `get_execution.executedNodesCount`.
